FanteQuiz

A Persian-first platform where fans of fantasy worlds play personality tests, quizzes and polls, and build their own for others to play.

Role
Designer: UX, UI, design system, prototype, usability testing
Platforms
Desktop and mobile, Persian, right-to-left
Scope
161 design frames, 4 roles plus guests, 3 game types
Tools
Figma, FigJam, Maze
Status
Version 1 tested; later changes not yet tested
Year
2026

Armin wrote the site's first roadmap, made the original banner artwork and redesigned some headers and dashboards that weren't used. Everything else on this page is my work.

The challenge

The three game types work in different ways. A quiz has right answers and a score. A personality test maps every answer to one or more possible outcomes. A poll has neither, only a spread of votes.

The platform had to make all three easy to play, including for first-time visitors without an account, and easy enough to build that fans would publish their own, while keeping user-made content safe through review. No user research came before the design; the usability test below is the first evidence from users.

Users and roles

Five kinds of user move through the product: four account roles plus signed-out guests.

UserWhat they can do
GuestBrowse and play any game; log in afterwards to keep the result
PlayerSave results and history; earn XP, levels, streaks and badges; follow people, rate and review games, appear in rankings
CreatorBuild tests, quizzes and polls, submit them for review, track their status, edit published games and see their analytics
Game adminReview submitted games in one assigned category: approve, return for edits with a reason, or refer to a site admin
Site adminRun the whole admin panel: all reviews, permanent deletion, users and roles, tickets, articles, reports and site settings (desktop only)

Information architecture

I organised the product into six areas: public pages, login and sign-up, playing, community, the user dashboard and the admin panel. The first site map had 43 pages; the design grew to 161 frames once error states, empty lists, modals and in-game interruptions were added.

Play, as a guest

  1. Find a game from the home page, or browse tests, quizzes or polls.
  2. Read the game overview: description, possible results, rules and top players.
  3. Play.
  4. See the result, then share it or log in to keep it.

Create a game

  1. Basic information and game type: test, quiz or poll.
  2. Results: outcomes for a test, score tiers for a quiz, result visibility for a poll.
  3. Questions and scoring.
  4. Publish settings: public or link-only, tags, category.
  5. Submitted, then in review, then approved and published, or returned with a reason.

Review a game

  1. The game enters the review queue with automatic checks: banned words, missing answers, and covers that resemble copyrighted images.
  2. A game admin for that category, or a site admin, approves it or returns it with a reason the creator sees in "My games".
  3. Game admins can refer a case to a site admin; only site admins can delete a game permanently.

Key design decisions

Play first, account later

Anyone can play without signing up. The result is kept temporarily, and a "keep your result" prompt leads to login only after the game.

An account wall before the first game would cost players before they see any value.

Passwordless sign-in

Accounts use an SMS verification code or Google and Apple sign-in, so there are no passwords to create, forget or recover. Phone, code and sign-up screens each have their own error states.

Fewer steps, and no recovery flow to design or support.

One wizard, three scoring models

Every game type is built in the same four steps, but steps 2 and 3 change with the type. A test assigns each answer option points towards one or more outcomes, with a panel showing how balanced the outcomes are. A quiz marks one correct answer per question and sorts players into score tiers. A poll has no scoring, and the creator chooses when results appear.

One familiar structure, with complexity only where a type needs it. Testing showed this is where the design is weakest.

Review before publishing, with scoped moderators

Submitted games pass automatic checks, then a human decision. Moderators give a reason when returning a game, and the creator sees it in "My games". Game admins see only their category; permanent deletion is reserved for site admins.

Keep user-made content safe without making one person a bottleneck. Both desktop test participants said they'd look for a rejected game's status in "My games", where the design puts it.

Designing the unhappy paths

The design covers 404, server-error and maintenance pages; in-game time-up, exit confirmation, loading and offline states; empty and loading states for six lists; and field-level errors in sign-in.

Mobile as its own layout

Mobile uses bottom navigation and a drawer, and game creation moves question editing into a bottom sheet. The admin panel stays desktop-only, with a clear notice on mobile instead of a cramped version.

Design system

I built a dark-theme system around one amber brand colour and a single Persian typeface, Vazirmatn, so that game artwork carries the colour and the interface stays quiet around it.

  • Foundations: 15 colour tokens, 4 spacing steps from 8 to 24 px, 6 corner radii, 3 shadows and 7 text styles.
  • Components: 44 component sets with 185 variants, plus 22 standalone components and 49 icons, from buttons and inputs to answer options with correct and wrong states, a game-type selector, an urgent timer chip, OTP fields and leaderboard rows.
  • Accessibility: every documented text colour pairing passes WCAG AA contrast; the lowest is muted text on panels at 5.1:1.
  • Still to fix: all text styles use a line height of 100, which is tight for Persian body text, and the subtle border colour is too faint to be the only cue that something is a control.

Usability testing

I ran two unmoderated prototype tests in Maze on version 1, one for desktop and one for mobile. Each mixed task-based missions with short questions and ended with the System Usability Scale. Maze recorded 4 desktop and 7 mobile sessions, but only 2 sessions per study reached the later tasks. Most respondents were 18 to 24.

TaskResultWhat the click paths showed
Find and play a personality test (desktop)4 of 4Most took the direct five-screen route; one detoured through login and other game types first
Share a result (desktop)3 of 3One step, no misclicks
Sign up to keep a result (desktop)InconclusiveOne reached the phone login; the other signed up by a route the test didn't count
Build and submit a personality test (desktop)1 of 2One stopped on the first step, reporting that its controls didn't respond; the other took over three minutes, with more than half of clicks outside interactive areas
Play an anime quiz (mobile)InconclusiveOne reached the score screen twice but wasn't counted; the other circled the game overview and ended up in login
Vote in a poll (mobile)InconclusiveBoth reached the poll results at step 3 but weren't counted
Find a notification setting (mobile)2 of 2One went straight to Settings; the other looked on the Notifications page first
  • Score matrix: the one participant who used it rated it 1 out of 5 for ease.
  • Mobile play: both mobile respondents rated playing a quiz on a phone as hard (1 and 2 out of 5), and both wanted to know immediately whether each answer was right.
  • Game overview: 3 of 4 desktop respondents read only one of the page's two notices.
  • SUS: 45 on desktop and 55 on mobile, from two respondents each; below the commonly cited average of about 68, but too few responses to interpret.

Design implications

  • Make the first step of game creation fully interactive, then retest building a test.
  • Test the score matrix on its own, with more participants.
  • Show right or wrong after each quiz question; the answer-option component already has those states.
  • Add a notification-settings link to the Notifications page.
  • Merge or reorder the two notices on the game overview page.

Limitations

  • Small samples. Two to four sessions per task show direction, not statistical significance.
  • Unmoderated and unrecorded. I can see where people went, but not why.
  • Test setup. Three tasks are inconclusive: participants reached valid end points that Maze didn't count, most likely because success was defined too narrowly. One mobile mission was edited mid-study, and the desktop prototype skipped the question screens of the personality test.
  • Untested changes. The design has changed since the test, and those changes haven't been tested.

What I learned

  • Define every valid ending before launch. Completed tasks were recorded as failures, most likely because each had a single success screen; only the click paths revealed it.
  • Prototype the interaction the task depends on. If a selector or a question screen isn't interactive, the test measures the prototype, not the design.
  • Small unmoderated tests need a second method. Next round I'll pair Maze with a few moderated sessions, so I can ask why.

Next steps

  1. Fix the creation wizard's first step and the score-matrix interactions.
  2. Retest building a test and playing on mobile, with at least five participants per platform and every valid ending counted.
  3. Link each change made since version 1 to the finding it answers, then show before and after.
  4. Raise body line height and strengthen control borders in the design system.

Divar redesign

An unofficial redesign of a popular Iranian classifieds app, made by a team of five designers in a six-day sprint.

My role
Listing and payment flow, full-app prototype, FigJam app flow, design-system work, case-study co-writing
Team
5 designers
Duration
6 days
Platform
Mobile app, Persian, right-to-left
Tools
Figma, FigJam
Type
Unofficial concept, not affiliated with Divar

The problem

Divar is a popular Iranian classifieds app where people buy and sell goods and services directly. Our review of the app found friction in three everyday tasks:

  • Signing in: login and sign-up shared one screen, and there was no Google or Apple sign-in.
  • Posting a listing: it took several tabs and screen changes to post a single listing, with no preview before publishing.
  • Chatting: chats had no useful filters and no read status, so people couldn't tell whether a message had been seen.

Users also couldn't edit their account details or delete their account.

Process

The team followed five design-thinking phases across six days.

  1. Empathise: a questionnaire, interviews, and a review of five classifieds apps (Craigslist, OLX, Facebook Marketplace, Sheypoor and Divar) against ten criteria, from search and filtering to trust and personalisation.
  2. Define: an empathy map and two proto-personas.
  3. Ideate: more than 40 paper sketches, and user flows for signing in and posting a listing.
  4. Design: a shared design system and high-fidelity screens for home, sign-in, posting and payment, chat and calls, "My Divar" and saved listings.
  5. Test: a clickable prototype of the whole app.

The empathy map pointed to three needs: trust in sellers and listings, more precise filters to save time, and a simpler chat.

Proto-personas

Both personas were built by the team from its research and assumptions, so they are proto-personas rather than research-validated profiles.

My part: posting a listing and paying to promote it

I designed the flow for posting a listing, the area where the old app made people switch screens most.

  1. Start from home. If the person isn't signed in, they sign in first, by phone or with Google or Apple.
  2. Fill in one listing form, with input checked before moving on, so errors are fixed in the form rather than after publishing.
  3. Preview the listing exactly as buyers will see it, the step the old app lacked.
  4. Choose whether to promote it. Promotion is a single yes-or-no step, so paying never stands between someone and posting a free listing.
  5. Pay, if they chose to promote.
  6. See "Under review", which tells them the listing isn't live yet and will appear once it is checked.

The prototype

I connected the team's screens into one clickable prototype of the whole app, with four starting points: login, chat and calls, Google sign-in, and the home page. It spans 35 frames, from sign-in, verification-code and error states to listing details, reporting a listing, saved listings, settings and profile editing.

The design system

The team built one shared system, and I contributed to it. Its components are grouped by area (sign-in, My Divar, saved listings, chat and calls, payment), alongside the colour palette, an icon pack and the logo. Type uses IRANSansX with six heading sizes from 32 to 12 px in three weights, with 16 px margins and a 50 px radius for rounded elements.

Testing and outcomes

The team ran interviews and a usability check on the prototype, but kept no notes, response counts or results, so I make no claim about how the redesign performed. The intended outcomes, none of them measured, were fewer steps to post a listing, more confidence before publishing, faster sign-in and clearer chats.

What I learned

  • Keep the evidence, even in a six-day sprint. We did the research but kept no records of it, so I can describe what we did but not what we found. On FanteQuiz I kept the test reports.
  • Build personas from data, or label them honestly. Ours mixed research with assumptions; calling them proto-personas is more accurate than presenting them as validated.
  • One prototype makes a team's work coherent. Connecting five designers' screens into a single prototype meant every flow had to share the same components and entry points.
